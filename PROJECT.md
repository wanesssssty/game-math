# Math Paws — інформація про проєкт

Документ узагальнює **ідею**, **покроковий план** (нашого типу курсової/кваліфікаційної роботи) і **фактичний стан** репозиторію. Детальні інструкції зі збірки, API й БД — у [README.md](./README.md), [documetation.md](./documetation.md), [server/README.md](./server/README.md) та [client/README.md](./client/README.md).

---

## Зв’язок із навчальним планом

Текстову основу покрокового плану взято з документа **«Розробка гейміфікованої освітньої платформи»** (орієнтир: вебзастосунок для арифметики з гейміфікацією). У репозиторії цей задум реалізовано під брендом **Math Paws** («лапки» + котячі аватари): той самий стек загалом (Next.js, Express, PostgreSQL, Prisma, Tailwind, shadcn/ui), але структура коду й деякі деталі API — як у поточному коміті, а не дослівно як у шаблоні з документа.

---

## Мета проєкту

Зробити **гейміфіковану освітню платформу** для вивчення арифметики:

- реєстрація та вхід, збереження прогресу на сервері;
- генерація та перевірка прикладів (додавання, віднімання, множення, ділення), рівні складності;
- підказки;
- ігрова валюта (цукерки), магазин, інвентар, кастомізація «котячого» аватара;
- журнал помилок і можливість працювати над помилковими відповідями;
- зрозумілий сучасний інтерфейс (адаптивність, доступність, послідовна навігація).

## Що вже є в репозиторії

### Інфраструктура й дані

| Область | Статус |
|--------|--------|
| Монорепозиторій `client` + `server` | Є |
| Docker Compose: Postgres, сервер, клієнт | Є |
| PostgreSQL 16, міграції Prisma | Є |
| Схема БД: користувачі, коти, кастомізація, прогрес, сесії, журнал помилок | Є |
| Сід: коти + товари магазину (`prisma/seed.js`) | Є |

### Бекенд (`server`)

Реалізовано REST API під префіксом `/api` (деталі — [server/README.md](./server/README.md)):

- публічно: health, реєстрація, логін, каталог магазину, збереження **гостьового** прогресу `POST /api/progress`, перегляд прогресу за ім’ям `GET /api/progress/:childName`;
- з JWT: нова задача, відповідь, підказка, покупка, інвентар, оновлення аватара, список помилок з `ErrorLog`.

Окремо варто пам’ятати: для авторизованого потоку **`GameSession` у БД не створюється** при кожній відповіді — сесії в такому вигляді пише головним чином гостьовий `POST /api/progress`; JWT-гра оновлює прогрес/цукерки/журнал помилок (див. серверний README).

### Фронтенд (`client`)

| Функція | Статус (станом на код у репо) |
|--------|--------------------------------|
| Сторінки режимів (`/addition`, `/subtraction`, …), змішаний тест, навігація | Є |
| UI (Tailwind, shadcn/ui), калькулятор, діалоги результатів | Є |
| Відправка завершеної сесії на **`POST /api/progress`** з fallback у `localStorage` | Є (`lib/progress-storage.ts`) |
| Сторінка **логіну** | Поки **демо** (немає виклику `/api/login`) |
| **Магазин / інвентар** у UI | Переважно **локальний стан** і статичний `store-items`, без викликів `/api/shop`, `/api/shop/buy`, `/api/inventory` |
| Гра «задача з сервера» (`/api/problem`, JWT) на всіх режимах | **Не підключено** — клієнтські ігри рахуються локально; бекенд для цього вже готовий |

Тобто **серверна частина охоплює майже весь функціонал з плану**, а **клієнт частково інтегрований**: надійно — збереження гостьового прогресу; решта флоу (логін, магазин за цукерки з БД, задачі з токеном) — **на етапі подальшої розробки**.

## Етапи з оригінального плану й відповідність реалізації

Нижче — узагальнення розділів з навчального документа. Оцінка **«у репо»** стосується саме цього git-проєкту, а не ідеального виконання всіх підпунктів на фронті.

| Етап (план) | Що очікувалось | У репозиторії |
|-------------|----------------|---------------|
| Архітектура, репозиторій, env | Клієнт + сервер, Git, секрети в `.env` | **Зроблено** |
| База даних | Prisma + PostgreSQL, моделі користувача, прогресу, магазину, помилок | **Зроблено** (моделі уточнені: коти, `UserCatCustomization`, тощо) |
| Бекенд | JWT, задачі, відповіді, підказки, магазин, інвентар, аватар, `/errors` | **Зроблено** на API |
| Фронтенд Next.js | Сторінки, зв’язок з API, токен, магазин, режим помилок | **Частково** (UI багато в чому є; повна інтеграція з API — ні) |
| UI (Tailwind, shadcn) | Акуратний адаптивний інтерфейс | **У процесі** (база є, полірування та зв’язка з реальними даними — далі) |
| Розгортання (Deploy) | Vercel / хостинг API / хмарна БД / CI | **Не описано в коді** як готовий пайплайн — типовий наступний крок |

Часові оцінки з оригінального документа (тижні на етап) залишаються орієнтиром для **звітності**, але фактичний прогрес краще відстежувати за таблицею вище та чеклістом нижче.

## Що планується зробити далі (пріоритети)

Узгоджено з цілями гейміфікованої платформи й поточними «прогалинами» між фронтом і беком:

1. **Авторизація на клієнті** — реальні `POST /api/register` та `POST /api/login`, збереження `data.token` (наприклад `localStorage` або httpOnly-cookie за бажанням), підстановка `Authorization: Bearer` у спільний API-клієнт.
2. **Ігровий цикл через бекенд** — після логіну отримувати задачу з `GET /api/problem`, відправляти `POST /api/problem/answer`, за потреби `GET /api/hint`; синхронізувати баланс цукерок і прогрес з відповідями сервера.
3. **Магазин і інвентар з API** — `GET /api/shop`, `POST /api/shop/buy`, `GET /api/inventory`; прибрати або залишити fallback на локальні дані лише для офлайн-демо.
4. **Аватар** — UI для вибору розблокованого кота та екіпіровки з куплених предметів (`POST /api/avatar/update`).
5. **Режим роботи над помилками** — екран, що читає `GET /api/errors` і пропонує повторне вирішення (можна спочатку локально з тим же `/api/problem`-подібним UX або окремим флоу).
6. **Якість і експлуатація** — автотести (API: Supertest; клієнт: за бажанням Vitest/Playwright), CI (lint, build, `prisma migrate deploy` на staging), документація деплою (Vercel + окремий хост для Express або один PaaS).
7. **Дрібниці** — оновити коментар у `progress-storage.ts` (ендпоінт уже існує); за бажанням об’єднати `documetation.md` і кореневий README, щоб не дублювати зміст.
